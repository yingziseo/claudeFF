> 2026-10-10 需求修订版。先收敛需求及技术方案，再开发。

## 一、项目目标

你现在是一名资深 Go 全栈工程师、Chromium 浏览器工程师、Windows 桌面客户端开发工程师和专业 UI/UX 设计师。

请开发一款真正可运行的 Windows 11 桌面客户端。

**软件名称：claudeFF**

**中文名称：Claude 防封工具**

这是一款专注于独立浏览器环境、住宅代理 IP 配置和浏览器指纹一致性管理的轻量级工具。

当前开发阶段为 MVP（最小可行产品）。

**最高原则：功能真实、架构简单、开发快速、方便测试。**

不要过度工程化，不要开发暂时用不到的商业模块。

### 当前明确不需要

- 不需要云端环境同步
- 不需要跨电脑恢复环境
- 不需要设备绑定
- 不需要会员套餐
- 不需要充值或购买
- 不需要支付宝或微信支付
- 不需要订单系统
- 不需要复杂管理后台
- 客户端环境数据不需要云数据库；后期授权服务可以有独立的卡密和用户数据库
- 不需要微服务
- 不需要复杂统计仪表盘
- 不需要自行编译完整 Chromium 源码
- 核心阶段暂不开展售卖流程；通过核心测试后再完成授权及可售卖版本

项目暂时只需要一个 Windows 客户端，以及必要的本地功能。

目标是先完成可以实际运行、使用和测试的原型。

## 二、技术栈

优先使用简单、成熟、编译快速的技术。以下是原方案起点；最新推荐仍为 Go + Wails 2 + React，最终结论以技术栈评审收敛后的方案为准。

| 模块 | 技术 |
|---|---|
| Windows 桌面框架 | Wails 2 |
| 后端语言 | Go |
| 前端 | React + TypeScript + Vite |
| 界面组件 | Tailwind CSS + shadcn/ui |
| 图标 | Lucide Icons |
| 本地数据库 | SQLite |
| 浏览器内核 | Chromium |
| 浏览器控制 | CDP / Go 浏览器控制库 |

不使用 Rust 和 Tauri。

Go 负责：

- 浏览器进程管理
- 代理 IP 连接与检测
- 环境配置管理
- 最后阶段的真实账号与联网卡密授权
- 数据持久化
- 浏览器启动和关闭

React 负责用户界面。

Tauri、Electron 等其他桌面框架不要随意引入。

### Chromium 要求

优先复用成熟的开源 Chromium 浏览器项目。

可以研究：

https://github.com/adryfish/fingerprint-chromium

以及其他合适的开源实现。

优先使用现成的可运行浏览器内核。

**不要为了完成 MVP 而从零编译 Chromium。**

必须保证每个环境能够启动独立 Chromium 浏览器进程，并使用独立的数据目录。

Wails 的网页视图只能用于管理界面，不允许将其冒充完整的 Chromium 指纹浏览器。

## 三、注册、登录与永久卡密：分阶段实现

### 1. 前期只实现注册登录的前端 UI 和交互

- 设计完整、精致的简体中文注册及登录页面，与主界面使用相同视觉规范。
- 可以预填测试内容，或者随意输入内容后点击登录进入主界面。
- 注册、登录不联网，不验证真实账号、密码或卡密，也不写入虚假授权记录。
- 开发入口明确标注开发模式，不能描述成已完成的正式安全认证。
- 这一跳过行为仅适用于用户明确批准的开发登录；代理检测、浏览器启动和持久化必须真实。

### 2. 真实账号与卡密在最后阶段接入

**浏览器核心功能及客户端测试通过后，再实现正式注册、登录、永久联网卡密以及卡密和用户管理面板。**

正式注册保留用户名、密码、确认密码和卡密。正式版本必须真实校验用户名、重复账号、密码基本长度、确认密码及卡密状态，不能沿用开发跳过逻辑。

正式登录支持保持登录、退出登录和明确的错误提示。密码采用安全哈希，记住登录不保存明文密码。真实身份、会话和授权校验不能只在前端进行。

### 3. 永久联网卡密

- 卡密默认永久授权，不增加到期套餐、续费、会员等级或窗口数量限制。
- 采用轻量联网激活服务，管理卡密生成、激活、重复激活和撤销。
- 签发工具或后台仅由开发者控制，签发私钥不得进入客户端、仓库或构建日志。
- 授权状态复核与永久授权分开定义；心跳、离线宽限、重复激活与恢复策略在授权阶段前明确。
- 当前没有新增设备绑定的决定，不默认按硬件绑定卡密。
- 联网激活有利于管理正常客户端的授权，但不能承诺客户端绝对无法被修改或破解。

### 4. 发布检查

最终售卖版本必须关闭开发登录跳过入口，通过真实注册、登录、激活、重复激活、撤销与离线边界测试。核心阶段的前端 UI 验证不替代上述后期验收。

## 四、住宅代理 IP：最重要的功能

**用户必须先配置代理 IP，才能创建和启动浏览器环境。**

这是项目最重要的业务流程。

### 1. 创建环境：第一步

弹出「创建浏览器环境」。

首先填写代理信息：

- 代理协议：HTTP / HTTPS / SOCKS5
- 代理服务器地址
- 端口
- 用户名
- 密码

提供「检测代理」按钮。

点击后进行真实网络检测。

必须显示：

- 连接是否成功
- 实际出口 IP
- 国家与地区
- 城市（可以获取时）
- 网络延迟
- 错误原因

不能使用虚假的网络检测结果。

如果无法可靠确认代理是否为住宅 IP，应明确标记「住宅属性未验证」，不允许伪造检测结论。

代理无法连接时，不允许创建可启动环境。

### 2. 代理认证

必须实际支持：

- 无认证代理
- 用户名密码认证
- HTTP 代理
- SOCKS5 代理
- 可兼容的 HTTPS 代理

对于 Chromium 不直接支持的认证方式，可以采用 Go 本地代理桥接。

但必须经过实际网络测试，不能仅保存配置就认为功能完成。

### 3. 一个 IP 只能运行一个浏览器窗口

这是强制要求。

**同一个实际代理出口 IP，同时只能被一个浏览器环境占用。**

例如：

环境 A：IP 1

环境 B：IP 2

环境 C：IP 1

A 和 B 可以同时启动。

A 已经启动时，C 不允许启动。

只有关闭 A 并释放运行占用后，C 才能启动。

必须通过 Go 后端校验，不允许只在前端限制。

当前是单机 MVP，只需要保证本机客户端内的 IP 互斥。

不需要跨设备分布式锁。

允许创建任意数量的环境，但必须遵守运行时 IP 独占规则。

### 4. 代理连接安全

启动浏览器前再次验证代理。

如果代理失效：

- 不允许直接使用本机公网 IP 代替
- 显示明确错误
- 提供重新检测按钮
- 支持重新启动环境

对于运行期间的代理故障，尽可能通过代理链路和进程控制实现禁止直连。

## 五、浏览器环境与指纹配置

### 1. 创建环境：第二步

代理检测成功后，进入环境配置。

用户填写：

- 环境名称
- 备注（可选）

其他参数尽量自动配置。

### 2. 自动生成一致性环境

根据代理检测结果生成合理的浏览器参数：

- 浏览器语言
- 时区
- 地理位置
- User-Agent（用户代理标识）
- 操作系统相关参数
- 屏幕分辨率
- 支持的其他浏览器指纹参数

优先保证配置与实际 Chromium 内核及 Windows 系统兼容。

同一个环境重复启动时，配置必须保持稳定。

不要每次启动随机生成新指纹。

对 Canvas（画布）、WebGL（图形渲染）、WebRTC（实时通信）等高级指纹项目，优先复用开源浏览器已有能力。

无法真实控制的参数，明确显示「暂不支持」。

**不能把保存一组模拟参数当成已经修改了真实浏览器指纹。**

不需要在 MVP 阶段自行修改或编译 Chromium 内核来实现全部高级指纹功能。

### 3. 环境隔离

每个浏览器环境必须拥有独立的：

- Chromium 浏览器进程
- 用户数据目录
- Cookie
- 本地存储
- 浏览器缓存
- 浏览历史
- 代理设置

关闭浏览器后，相关数据应保留。

重新启动相同环境时，继续使用该环境原有的浏览器数据。

### 4. 环境管理功能

主界面只需要：

- 创建环境
- 启动环境
- 关闭环境
- 编辑环境
- 删除环境
- 搜索环境
- 查看运行状态

不限制创建环境数量。

不需要复杂的环境分组、团队协作、权限系统和自动化任务。

## 九、开发环境与云端构建

当前目录用于阅读、编辑代码和文档，以及 Git 操作。当前服务器配置较弱，**禁止在本机或 Codespaces 执行项目构建、编译性测试及高负载依赖安装**。

所有依赖安装、Go 测试、类型检查、前端构建、Wails 构建和打包默认使用 GitHub Actions。需要编译的开发命令也不得在当前服务器执行。

### 1. Windows 云端构建

GitHub Actions 使用 Windows 运行器，安装经过验证并锁定版本的 Go、Node.js、Wails 2 及必要构建依赖，生成 Windows x64 客户端并上传 ZIP 构建产物。

最终产物包含能够运行的 `claudeFF.exe` 和必要说明，浏览器内核的随包交付方式在技术方案中确定。源码 ZIP 是额外开发材料，不替代已编译客户端。

### 2. 云端验证与状态报告

- 可移植 Go 模块测试、前端类型与构建检查、代理测试和浏览器集成验证都在云端执行。
- 编译成功、云端浏览器集成测试和真实 Windows 桌面启动分别记录。
- 没有经过 Windows 真实启动验证的功能必须注明未验证，不编造测试结果。
- 工作流记录提交 SHA，重大更新日志引用实际验证状态，失败必须分析并修复。

### 3. 编译效率

采用缓存、按改动范围检查、手动触发及取消过期构建。避免反复完整构建、自行编译 Chromium、复杂容器编排以及把热更新构建移回当前服务器。

## 十一、执行顺序

普通技术细节自主决定，不反复询问。先完成需求沟通、技术方案和文档，之后按以下阶段开发：

**第一步：文档与工程基线。** 写入 AGENTS.md、工作日志、需求修订、UI/UX 及技术方案；建立最简工程和 GitHub 云端构建流程。技术栈尚未定稿时不擅自替换原框架。

**第二步：前端先行并等待风格认可。** 建立接近苹果原生应用的简约中文界面，完成可跳过的注册登录、主界面和交互设计，通过网页链接提供预览。用户认可设计风格后，再开始独立 Chromium 启动、关闭和环境数据隔离的后端开发。

**第三步：真实代理与 IP 独占。** 实现代理检测、认证桥接、Chromium 网络复核、运行期故障处理和 Go 后端 IP 互斥。

**第四步：环境持久化与一致性参数。** 实现环境创建、编辑、删除、搜索、稳定指纹、SQLite 和安全存储；逐项接入真实 UI 操作。

**第五步：核心验收。** 完成 Chromium 环境首页、主题和状态反馈，执行核心测试并修复问题；在 Windows 云端构建和真实 Windows 环境分别验证。

**第六步：最后加入商业授权。** 在核心测试没有问题后，实现真实账号、永久联网卡密，以及轻量的卡密和用户管理面板。该阶段再明确授权主体、心跳、离线和重复激活策略。

**第七步：最终发布验收。** 检查真实授权替换开发登录、前后台安全边界、Windows 运行及免安装 ZIP，交付源代码、运行说明和真实测试报告。

任何阶段都不能用静态假结果冒充代理、浏览器或持久化。前期注册登录 UI 跳过是明确批准的开发例外。

## 十二、严格限制

请牢记：

**这是 MVP，不是完整商业 SaaS（软件即服务）平台。**

不要自行增加：

- 云同步服务
- 支付系统
- 会员套餐
- 邮件验证码
- 手机验证码
- 商业运营后台
- 无关用户行为分析系统；后期后台仅允许约定的基本使用概况
- 团队协作
- 远程浏览器控制
- 复杂的权限体系
- Kubernetes
- Redis
- 大型微服务架构

也不要为了设计一个漂亮的界面而忽略真实 Chromium 启动和代理功能。

核心阶段只需要真实解决：

**开发登录进入 → 添加代理 → 检测 IP → 生成环境 → 启动 Chromium → 独立浏览 → 保存环境。**

核心通过测试后，最后增加真实注册登录、永久联网卡密及卡密和用户管理面板。除此之外的支付、套餐和云同步仍不纳入范围。

浏览器隔离和指纹一致性可以降低不同测试环境之间的相互干扰，但不能保证任何网站账户不会受到限制。

## 十四、最后阶段的卡密和用户管理面板

这是核心浏览器测试通过之后的后期功能，不能提前占用核心开发优先级。

至少包含：

- 卡密生成或导入、查询、激活状态和撤销。
- 已激活用户列表，显示约定的用户名、卡密关系、激活时间与授权状态。
- 用户在线状态、最近上报时间、客户端版本，以及约定的基本使用概况。
- 最小必要的管理员认证和权限检查、HTTPS 与关键操作记录。

在线状态通过心跳推算，不能承诺实时绝对准确。不默认收集 Cookie、浏览历史、网页内容和代理秘密。具体授权、重复激活、离线宽限与恢复策略在该阶段前收敛。
